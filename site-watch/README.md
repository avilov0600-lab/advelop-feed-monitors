# Подтверждение недоступности сайтов и личные уведомления

Отдельная служба Timeweb `advelop-site-watch.service`. Работает без GitHub Actions, GitHub API, AI-запросов и новых внешних сервисов. Использует существующие проверки HTTP/TLS и Telegram transport. Проверяет только публичные сайты из `sites.json`; XML, кабинеты площадок и источники лотов не опрашивает.

## Правило уведомлений

1. Неудачная проверка сайта в обычном отчёте начинает инцидент (раунд 0).
2. Дополнительные HTTP-проверки выполняются через 15 минут и ещё через 15 минут. Повторный неудачный обычный отчёт не ускоряет подтверждение.
3. После третьего неудачного раунда отдельное сообщение отправляется в личку активным подписчикам бота соответствующего клиента. Перед отправкой заново проверяется подписка и соответствие токена ожидаемому боту.
4. Если сайт восстановился до подтверждения, отдельной тревоги нет. Во время длительного сбоя проверки продолжаются раз в 15 минут, повторные тревоги по этому инциденту не создаются.
5. После восстановления отдельное сообщение получают те, кому удалось доставить тревогу и кто всё ещё подписан.

Внутри одного HTTP-раунда — до трёх коротких попыток (таймаут 8 секунд, пауза 2 секунды). Это не заменяет разнесённые на 15 минут раунды. HTTP 200–399 считается доступным. HTTP 403 означает ограничение доступа для проверяющего сервера и отражается причиной; это не доказательство недоступности для всех посетителей. Отсутствующий адрес и ошибка кода проверки не объявляются сбоем сайта.

## Откуда берутся данные

- Основные отчёты по-прежнему формируются в 09:00, 13:00, 15:30, 18:30 МСК.
- Для 12 ботов служба читает `site_availability` из `/var/lib/TENANT-feed-monitor/latest.json`.
- Для MASTERS — только первую строку статуса и время сохранённого отчёта из `latest` общей базы `/var/lib/advelop-telegram-relay/relay.sqlite3`.
- Изменения локальных отчётов отслеживаются раз в 15 секунд, без сетевых запросов. Принимаются только новые наблюдения не старше 30 минут с часовым поясом.
- Если основной отчёт задержался, предусмотрены резервные HTTP-проверки в 09:10, 13:10, 15:40, 18:40 МСК. Свежая успешная проверка обычного отчёта отменяет соответствующий резервный запрос. При первом запуске без свежего наблюдения сайт проверяется сразу.
- Одинаковые адреса внутри одного клиента объединены. Совкомбанк присутствует в конфигурации без адреса сайта: до получения адреса его сайт не проверяется.

## Подписки и безопасность

Существующие базы подписчиков открываются только для чтения, с фильтром `tenant=? AND active=1`. Доставляются только личные чаты с положительным chat ID. `/start`, `/stop`, мгновенная выдача последнего отчёта и плановые рассылки остаются в существующих службах.

Токены читаются на сервере из существующих защищённых настроек. В конфигурации и этом репозитории токенов и идентификаторов подписчиков нет. Служба не принимает входящие соединения, запускается с ограничениями systemd и пишет состояние в собственный каталог. Для чтения живых WAL-баз разрешены служебные файлы координации SQLite в каталогах реестров; сами основные файлы баз защищены `ReadOnlyPaths`, соединения открываются с `mode=ro`. Root нужен для чтения уже существующих закрытых настроек ботов.

## Состояние и доставка

Собственная SQLite-база `/var/lib/advelop-site-watch/state.sqlite3` сохраняет следующие проверки, инциденты и очередь доставки. Перезапуск не сбрасывает 15-минутные интервалы. Один процесс обеспечивается блокировкой файла. Сетевые сбои и HTTP 429 Telegram повторяются с задержкой; заблокировавший бота получатель не мешает остальным. Ошибки 400/403 сохраняются для диагностики, без бесконечного повтора.

Уникальность `(инцидент, получатель, тип сообщения)` предотвращает повторное создание тревог. Как у обычной Telegram Bot API-доставки, при аварии строго между успешным ответом Telegram и фиксацией SQLite возможен повтор: гарантии exactly-once от Telegram нет.

## Установка и проверка

`install.py` принимает подготовленный каталог с тремя файлами и `hashes.json`, проверяет SHA-256 и синтаксис, затем создаёт только новые пути. При существующих файлах/состоянии останавливается для проверки. Не меняет старые приложения и базы. При ошибке останавливает только новую службу, оставляя состояние для диагностики.

Проверка конфигурации и наличия доступных настроек/реестров:

```sh
PYTHONPATH=/opt:/opt/advelop-command-intake python3 /opt/advelop-site-watch/watch.py --config /etc/advelop-site-watch/sites.json --preflight
systemctl status advelop-site-watch.service
journalctl -u advelop-site-watch.service
```

Логи содержат тип события, код ответа, клиента и номер раунда, без токенов и chat ID. Обновляя клиентов/адреса, нужно синхронно обновить `TENANTS`, конфигурацию и тесты, проверить отображение реестров и настроек, затем перезапустить только эту службу. Состояние существующих URL сохраняется.

Офлайн-тесты: `python3 -m unittest discover -s tests -p test_site_watch.py` из корня репозитория.
