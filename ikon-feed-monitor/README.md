# IKON DEVELOPMENT Feed Monitor

Отдельный монитор IKON DEVELOPMENT. Он не использует токены, состояние или
расписание MASTERS. В отчёте остаётся только раздел **Жилая недвижимость**.

## Рабочая инфраструктура — 12 октября 2026

Монитор перенесён на существующий Timeweb VPS `77.232.136.244`.
Загрузка клиентских фидов, исходящих XML, карточек, API и отправка Telegram
выполняются с этого сервера. Только клиентские материнские XML закреплены за
IPv4 в коде загрузчика (без отключения проверки TLS); для Telegram сохранён
IPv6 (`TELEGRAM_IP_FAMILY=ipv6`), поскольку его IPv4 с этого VPS недоступен.
Клиенту необходимо разрешить `77.232.136.244/32` на обоих материнских XML.

- Код: `/opt/ikon-feed-monitor`; пользователь `ikon-monitor`.
- Секреты: `/etc/ikon-feed-monitor.env`, root-only, права 600.
- Отчёт, состояние и снимки: `/var/lib/ikon-feed-monitor`, права 700.
- Планировщик: `ikon-feed-monitor.timer`; процесс: `ikon-feed-monitor.service`.
- Рассылка обращается к существующему локальному relay на 127.0.0.1:8765.
  Реестр `/var/lib/advelop-telegram-relay/relay.sqlite3`, tenant `ikon`,
  сохранён без замены; MASTERS и DAR не изменены.
- GitHub хранит исходники и ручной диагностический workflow. Автоматический
  cron удалён; `IKON_MONITOR_ENABLED=false` — дополнительная защита.
- Рабочий монитор не зависит от Yandex Cloud, Sites или GitHub API.
  Старые облачные ресурсы не удалены и не используются как планировщик.

Команды обслуживания:

```sh
systemctl list-timers ikon-feed-monitor.timer
systemctl status ikon-feed-monitor.service
journalctl -u ikon-feed-monitor.service --since today
systemctl start ikon-feed-monitor.service  # внеплановая проверка и рассылка
```

Проверка недоступного материнского источника остаётся красной, количество
не подменяется нулём. Перенос не обходит IP-фильтр клиента.

## Логика сравнения

1. По каждому проекту и категории сопоставляются ID эталона и каждого XML:
   невыгруженные лоты, лишние лоты, дубли ID и записи без ID.
2. По совпавшим ID сравниваются тип сделки, площадь, комнатность, этаж,
   этажность и номер квартиры — если поле есть в обоих источниках.
3. Цены жилой недвижимости сравниваются между исходящими фидами: клиентский
   XML может содержать цену до рекламной скидки. В Яндексе при наличии берётся
   `discount/final-price`.
4. Между исходящими фидами сравниваются состав и сопоставимые поля.
5. Отмечаются истёкшие даты акций и упоминания уже прошедших месяцев в
   рекламных формулировках. Это сигнал для проверки текста, а не юридическое
   заключение о действительности акции.
6. Циан: число опубликованных объявлений и ошибки импорта через API.
   Авито: число активных объявлений через API. Это проверка количества по
   аккаунту/категории, не полное сопоставление каждого объявления API с XML.
7. Активные карточки ЖК: Циан и Яндекс проверяются по публичной странице,
   если страница отдаёт распознаваемое число. При блокировке/изменении вёрстки
   карточка честно отмечается как не проверенная автоматически.
8. Домклик — согласованный контроль по фиду: его количество должно совпадать
   с остальными XML проекта. Это не чтение личного кабинета Домклик.

Красные строки из клиентского документа на сентябрь исключены из размещений:
Яндекс/Новый Зеленоград и Авито/Skolkovo ONE. Их XML продолжают проверяться,
но карточки не выводятся. Ожидание для жилого API Авито включает только Новый
Зеленоград. Исключения не включатся автоматически в октябре — нужен пересмотр
`PLATFORM_CARDS` и `API_ACTIVE_PROJECTS`.

## Цвета

В Telegram категории и названия ЖК выделены жирным, проекты разделены пустыми
строками. Подписи эталона, площадок и времени проверки — курсивом. Площадки
показаны внутри своего проекта, API — отдельно в конце категории. Даты выводятся
по Москве в формате `03.09.2026, 13:01:48 МСК`.

Блок «Объявления в кабинетах — по API» показывает два числа: количество в
кабинете и ожидаемое количество в фидах. В каждой строке указан охват: оба ЖК
или конкретный активный ЖК. Совпадение количества не означает поштучную
проверку объявлений или верификацию аккаунта. Строки `covered_by_api` не
дублируются под проектами, если эти числа доступны и совпадают: результат
виден один раз в блоке кабинетов. Доступные числа сохраняются и при ошибке;
нет данных не подменяется нулём. Ошибки импорта Циан остаются красными даже
при совпадающем количестве. Эти правила действуют и в кратком отчёте.

Формат — Telegram HTML, все значения из источников экранируются. Прямая
рассылка, приватное хранилище, функция `/start` и relay сохраняют `parse_mode=HTML`.
Старые сохранённые сообщения без этого поля остаются обычным текстом. При
большом числе ошибок краткий вариант сохраняет жилую категорию и разделители.

Строка «Даты и месяцы акций» показывает результат существующих правил: истёкшие
`end_date`/`end-date`/`DateEnd` и старые месяцы рядом со словами «скидка», «акция»,
«ипотека». Это не сплошная редакторская проверка описаний и не проверка любых
произвольных дат в тексте. Чужие бренды, контакты, служебные вставки и другие
лишние вводные автоматически пока не определяются. Для них нужны согласованные
правила. Ошибки акций выводятся даже при недоступном эталоне; непрочитанный фид
не получает отметку «замечаний нет».

- 🟢 Жилая категория: все обязательные эталоны, фиды и API доступны; сравнения прошли.
- 🔴 Жилая категория: источник недоступен, состав/поля/цены расходятся, есть ошибка
  рекламного текста или API не подтверждает публикацию.
- Общий цвет красный, если красная хотя бы одна категория.
- ⚪ У отдельной публичной карточки означает, что число не удалось прочитать.
  Это не означает «0 объявлений» и само по себе не отменяет API-проверку.

Если источник недоступен, отчёт показывает `SOURCE_UNAVAILABLE` и пустое
значение количества, а не ложный ноль. Остальные источники проверяются дальше.

## Запуски и нагрузка

Ежедневно четыре отчёта: **09:00, 13:00, 15:30 и 18:30 МСК**.
Рабочий systemd timer с явной зоной Europe/Moscow:
`09,13:00:00` и `15,18:30:00`. Лимит процесса — 8 минут.
Один systemd service не запускается параллельно самому себе.
После простоя `Persistent=true` выполняет одну догоняющую проверку.
Интенсивное расписание первой недели отменено; переменная
`IKON_INTENSIVE_STARTED_AT` больше не влияет на запуски.
Расписание включается командой `systemctl enable --now ikon-feed-monitor.timer`.

В GitHub нет расписания, push/PR-триггеров или опроса репозитория с VPS.
Ручной диагностический запуск GitHub оставлен для оператора; он использует
динамический IP GitHub, поэтому закрытые клиентские XML там могут быть недоступны.
`schedule_policy.py` сохранён для совместимости ручного workflow.
Режимы:

- `digest` — полная проверка и сообщение сразу;
- `monitor` — уведомление после двух одинаковых ошибок подряд, затем только
  при изменении проблемы или восстановлении.

Один проход загружает 2 клиентских XML, 8 исходящих XML,
до 3 публичных карточек, 1 снимок Циан и 1 снимок Авито.
Один снимок Циан — обычно 2 запроса. Один снимок Авито — авторизация и
страницы списка по 100 объявлений. Запросы к 6feeds идут последовательно.
Сетевые ошибки скачивания XML: максимум 3 попытки с паузой 2 секунды.
HTTP 401/403/404 не повторяются. Код не обращается к GitHub API.

Лимит ручного GitHub job — 8 минут; клонирование с глубиной 1. Внешних Python-зависимостей
нет, установка и pip-cache не нужны. Артефакт — только `reports/latest.json`,
хранение 1 день. Состояние подавления уведомлений кэшируется только для
ручного режима `monitor`; расписание Timeweb всегда отправляет дайджест.

## Подписка и последний отчёт новому пользователю — прежняя облачная схема

Этот раздел ниже описывает историческую конфигурацию Яндекса, а не рабочий
маршрут после переноса. Сейчас монитор сохраняет последний HTML-отчёт в
локальном multi-tenant relay Timeweb и получает список активных подписчиков.
Telegram /start и /stop обслуживает тот же relay через существующий публичный
webhook Timeweb; он возвращает последнее сообщение без новой проверки источников.
Ключ и tenant IKON отделены от MASTERS. Старые документы ниже сохранены
для справки и не являются инструкцией повторно включать облачную схему.

GitHub сохраняет дайджест напрямую в отдельной Yandex Cloud Function через
`TELEGRAM_LATEST_MESSAGE_URL`, получает список активных подписчиков и отправляет
сводку каждому из них. Входящий `/start` проходит
по маршруту:

`Telegram → публичный relay IKON → API Gateway IKON → Cloud Function → Object Storage`.

Функция из `yandex_cloud/index.py` сохраняет подписку и возвращает последний
текст с подтверждением «Автоматические обновления подключены» через шлюз и
relay обратно Telegram. Она не запускает монитор и не вызывает GitHub.
Публичный webhook: `https://ikon-telegram-relay.avillius.chatgpt.site/telegram`.
Обычный GET корня адреса показывает только техническое состояние, не отчёт.
Relay не хранит токен бота или отчёты, не пишет прикладные логи, не обращается
к источникам. Он передаёт только ID обновления, ID личного чата, `/start` и
проверочный заголовок Telegram. Ответ проходит через relay без кэширования.
Запрос без заголовка отклоняется; значение заголовка проверяет функция Яндекса.
Произвольные действия (включая сохранение отчёта), группы, cookie и имена
пользователей relay не передаёт. Перенаправления внешнего запроса запрещены.

Для функции нужны:

- Python 3.12, entrypoint `yandex_cloud.index.handler`;
- код `monitor.py`, `config.py`, папка `yandex_cloud`;
- `TELEGRAM_BOT_TOKEN` из отдельного секрета;
- приватный RW mount Object Storage в `/function/storage/state`;
- webhook Telegram с `secret_token = sha256(TELEGRAM_BOT_TOKEN)`;
- отдельный bucket/prefix и ограничение одновременных вызовов до 1, чтобы
  файловое состояние `/start` не менялось конкурентно.

Функция возвращает Telegram команду `sendMessage` в HTTP-ответе, поэтому
исходящий доступ из Yandex Cloud к Telegram для `/start` не нужен.
Повторные `/start` одного чата в течение 60 секунд подавляются.
При этом подписка сохраняется до ограничения повторного ответа. Если отчёта
ещё нет, человек всё равно подписывается и получает подтверждение. Подписчики
хранятся отдельными объектами `ikon-subscribers/<chat_id>.json` в закрытом
IKON-хранилище: только ID, статус и номер/время команды, без имён и профилей.
Для небольшой командной рассылки установлен защитный лимит 100 записей.
Твой `TELEGRAM_CHAT_ID` добавляется один раз при первой авторизованной
синхронизации. Повторный `/start` не создаёт дублей. Ошибка доставки одному
человеку не прерывает попытки отправить остальным; временные ошибки отражаются
в результате запуска. HTTP 403 от Telegram отключает недоступного получателя,
не отменяя более новый `/start`. Для прекращения уведомлений можно заблокировать
бота; после разблокировки `/start` снова подключает рассылку.

До этой доработки IKON не сохранял получателей `/start`, поэтому существующим
пользователям нужно нажать команду повторно. Расписание от этой доработки
не меняется. MASTERS использует другой реестр и не получает данные IKON.

Синхронизация требует дату проверки с часовым поясом и не позволяет старому
отчёту заменить более новый. Доступ к сохранению текста защищён токеном бота;
webhook проверяет отдельный заголовок с SHA-256 токена.
Старый отчёт также не рассылается поверх нового. Закрытые служебные действия
`subscription_status` и `mark_unreachable` требуют сырой токен IKON, а не
Telegram webhook-подпись; публичный relay их не пропускает. В журналах рассылки
выводятся только количества получателей, доставок и ошибок, не ID или токены.

## Локальная проверка

```bash
python3 -m unittest discover -s tests -v
python3 monitor.py --cache-dir .cache --output reports/latest.json
python3 monitor.py --offline --cache-dir .cache --output reports/latest.json
```

Без `--send-telegram` сообщения не отправляются. Отсутствующий API-секрет
показывается как незавершённая проверка API. Значения секретов и идентификатор
личного Telegram-чата хранятся только в настройках GitHub Secrets.
